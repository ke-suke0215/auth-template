# Issue 対応からマージまで

## 概要

GitHub の Issue URL または Issue 番号を受け取り、Issue の要件を満たす変更を実装する。最新の `main` から専用 worktree を作成して作業し、PR を作成し、CI とサブエージェントレビューを通過させてからマージする。`main` に直接実装しない。

## 基本方針

- ユーザーが指定したリポジトリと Issue の範囲内で作業し、無関係な変更を勝手に含めない。
- 編集前に Issue の要件、完了条件、リポジトリの状態、既存のガイドを確認する。
- Issue ごとに新しい worktree とブランチを作成する。ブランチ名は、原則として `codex/issue-<番号>-<短い名前>` とする。
- Issue・PR の情報、コメント、レビュー結果、GitHub 上の更新には GitHub コネクターを優先する。worktree、ブランチ、コミット、push、Actions の確認にはローカルの `git` と `gh` を使う。
- サブエージェントのレビュー結果をメインエージェント自身が確認し、すべての有効な指摘を解消し、必須 CI が成功するまでマージしない。
- 指摘があった場合は、差分と Issue 要件に照らして妥当性を確認する。妥当な指摘を修正したら、関連チェックを再実行し、コミットと push を行い、もう一度レビューを依頼する。この流れを指摘がなくなるまで繰り返す。
- サブエージェントには、実際の PR 差分と Issue 要件を確認させる。コードは変更させず、レビュー結果を PR の Conversation にトップレベルコメントとして投稿させる。

## 手順

### 1. `main` に戻して最新化する

1. `git status --short --branch` と `git worktree list` で状態を確認する。
2. 無関係な変更を保護する。現在の worktree が汚れている、または Issue 対応に含めてよいか判断できない変更がある場合は、編集せずに確認を求める。
3. 現在の checkout を `main` に切り替え、`origin/main` を取得して fast-forward する。reset やコミットの破棄は行わない。

### 2. Issue を取得して要件を整理する

1. Issue URL からリポジトリと Issue 番号を取り出す。番号だけの場合は、ローカルの `origin` からリポジトリを解決する。
2. Issue 本文とコメントを取得する。完了条件、対象ファイル、制約、必要な検証を整理する。
3. リポジトリの構成、関連コード、既存テスト、workflow、ローカルの指示書を確認する。

### 3. 専用 worktree を作成する

最新化した `main` から、例えば次のように worktree を作成する。

```sh
git worktree add -b codex/issue-<番号>-<短い名前> /private/tmp/<リポジトリ名>-issue-<番号> main
```

実装、検証、コミットは専用 worktree 内で行う。元の checkout は `main` のまま保つ。

### 4. 実装と検証を行う

1. Issue の完了条件を満たす最小限の変更を実装する。
2. 動作変更がある場合はテストを追加または更新する。
3. リポジトリの formatter、lint、型チェック、テスト、build、Issue 固有の検証を実行する。CI と同じコマンドを優先する。
4. `git diff`、`git diff --check`、`git status` を確認し、意図したファイルだけを stage する。

### 5. コミット、push、PR 作成を行う

1. 変更内容を簡潔に表すメッセージでコミットする。
2. ブランチを upstream 付きで push する。
3. ユーザーが Ready 状態を明示していない場合は、`main` 向けの Draft PR を作成する。PR 本文には変更内容、理由、影響、修正の場合の原因、検証内容、`Closes #<番号>` を含める。
4. 必須 GitHub Actions の完了を待つ。失敗した場合はログを確認し、原因を修正してからレビューに進む。

### 6. サブエージェントレビューを繰り返す

読み取り専用の範囲を明確にしたサブエージェントを起動する。依頼には次を含める。

- 実際の PR 差分、Issue の要件、現在の CI 状態を確認すること。
- コードや worktree を変更しないこと。
- 指摘がなければ `指摘なし` と確認項目を PR の Conversation に投稿すること。
- 指摘があれば、重要度、ファイルと行、理由、具体的な修正案を PR の Conversation に投稿すること。
- レビュー結果とコメント URL をメインエージェントへ返すこと。

サブエージェントの処理が終わったら、PR のコメントを GitHub から取得して、投稿されたレビュー本文をメインエージェント自身で確認する。サブエージェントの完了報告だけを根拠にしない。

指摘がある場合は、次の手順を繰り返す。

1. 各指摘をコードと Issue 要件に照らして確認する。
2. 妥当な指摘をすべて専用 worktree で修正する。
3. 関連チェックを再実行し、コミットして push する。
4. 新しい CI の完了を待ち、サブエージェントに再レビューを依頼する。文脈を安全に引き継げる場合だけ、同じサブエージェントへの追加依頼を使う。
5. 指摘がなくなるまでこのループを続ける。

指摘がなければ、最終処理へ進む。

### 7. Ready 化してマージする

1. PR が open であること、head SHA が最新であること、必須 CI が成功していること、未解決の有効な指摘がないことを確認する。
2. Draft PR を Ready for review に変更する。
3. ユーザーやリポジトリの指定がなければ squash merge する。利用できる場合は、確認済みの head SHA を指定する。
4. PR が merge 済みであること、Issue がクローズされていることを確認する。PR、レビューコメント、merge commit、検証結果、worktree の場所を報告する。

## 失敗時の対応

- Issue が曖昧、要件が衝突、または worktree に無関係な変更がある場合は、編集前に確認を求める。
- CI が失敗した場合は未解決として扱い、ログから根本原因を調べ、修正、push、再実行を行う。
- 指摘が妥当でない、または Issue の範囲外である場合は、理由を PR に説明して再レビューを依頼する。黙って無視しない。
- 必須チェック、権限、競合、ブランチ保護などでマージできない場合は PR を open のまま残し、具体的な阻害要因を報告する。強制マージは行わない。
